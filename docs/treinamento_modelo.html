Como o modelo é treinado.

Da configuração de um braço experimental à última rodada: criação dos clientes, inicialização pareada, otimização local por tarefa, agregação do tronco compartilhado, validação e persistência dos checkpoints.

A unidade real do treinamento

Cada cliente conhece um dataset e uma tarefa. Ele atualiza o modelo completo localmente, mas somente o tronco compatível viaja até o servidor.

cliente = dataset × tarefa × partição
artefato final = tronco global + parte personalizada

01 · Escopo

Três formas de executar

O repositório possui rotas clássicas para um único dataset e uma rota federada multi-dataset. O estudo principal usa a terceira rota e cria pares federado versus local-only sob o mesmo orçamento e a mesma partição.

MTL

Treino centralizado

training_multitask.py aprende segmentação e classificação quando cada linha possui as duas supervisões. É válido para BUSI, mas não para o ISIC multi-tarefa disjunto.

1×

Treinos por tarefa

training_segmentation.py e training_classification.py treinam uma tarefa por vez. As variantes _prod unem treino e validação.

FedPer

Treino federado

training_federated.py atende BUSI + ISIC, com clientes de tarefa única, tronco compartilhado e partes personalizadas.

Este documento acompanha a rota FedPer.

Ela também implementa o baseline local-only: com federated.standalone: true, os clientes recebem a mesma inicialização, mas deixam de aceitar o tronco agregado nas rodadas seguintes.

02 · Planejamento reproduzível

O estudo é resolvido antes de treinar

O study_runner combina cada seed com cada braço do manifesto. Para cada combinação, grava uma configuração YAML imutável, calcula hashes e aponta todos os braços da mesma seed para uma única partição pareada.

Confere assinatura e SHA-256. Uma partição existente só é reutilizada quando metadados e conteúdo correspondem.

Executar sequencialmente

Roda cada braço, atualiza run_index.csv e preserva execuções incompletas para retomada explícita.

Desenho de avaliação suportado

CV = 1 · holdout

Configuração base atual

Uma separação externa determinística. Com holdout_test_size: 0.30, 30% fica para teste e os 70% restantes formam o pool de treino + validação.

Os resultados são descritivos; não há Wilcoxon.

CV ≥ 2 · cross-validation

Alternativa suportada

Cada fold usa uma fatia externa diferente como teste. A mesma configuração de fold é compartilhada entre braços pareados.

Diagnósticos Wilcoxon permanecem exploratórios porque cliente × fold não são réplicas independentes.

05 · Pareamento

A aleatoriedade também é controlada

Seeds estáveis são derivadas de seed base, fold, cliente, fase e rodada. Isso pareia inicialização, ordem dos dados e transformações entre o braço federado e seu baseline local-only.

seed_cliente = SHA-256(seed_base | fold | client_id | fase | rodada)
O orquestrador também reinicializa o tronco global por fold. Assim, a criação de modelos de um fold anterior não desloca o gerador aleatório do fold seguinte.
A

Inicialização local

Stem, decoder e cabeça começam iguais entre braços pareados do mesmo cliente.

B

Ordem de dados

Shuffling ou sampler rotativo recebe uma seed estável, independente da recriação do worker Ray.

C

Transformações

Flips e rotações sorteiam a partir da seed de cliente, fase e rodada.

06 · Rodada federada

O ciclo completo de uma rodada

Todos os clientes participam de fit e validação. Falhas não são aceitas silenciosamente: com accept_failures=false, uma falha impede a agregação daquela rodada.

Servidor envia o tronco

Na primeira rodada, usa a inicialização global pareada. Depois, envia o resultado agregado anterior.

Cliente recompõe o estado

Carrega optimizer e parte personalizada de state.pt; no federado, injeta o tronco recebido.

Otimização local

Executa forward, calcula a perda da tarefa, faz backward e atualiza tronco + parte local.

Validação local

Mede loss e Dice ou acurácia no split val, sem transformações geométricas.

Persistência local

Salva o estado da rodada. Se a loss melhora, grava também um best.pt diagnóstico.

Agregação

Somente o tronco atualizado retorna. O servidor calcula os pesos, agrega e registra participação.

07 · Orçamento local

Steps e epochs medem esforços diferentes

Esse é um dos eixos mais importantes do estudo. Os dois modos usam o mesmo loop de otimização, mas definem de modo distinto quando o cliente encerra sua contribuição da rodada.

Modo steps

Cada cliente executa exatamente steps_per_round updates. O sampler rotativo percorre um fluxo determinístico de permutações e muda o ponto inicial a cada rodada.

Efeito: trabalho computacional local igual, independentemente do tamanho do cliente.

ou

Modo epochs

Cada cliente percorre seu loader completo por local_epochs. Clientes maiores processam mais batches e mais imagens.

Efeito: esforço proporcional ao tamanho efetivo da base local.

Comparação válida exige orçamento pareado.

Federado em steps deve ser comparado ao local-only em steps; federado em epochs ao local-only em epochs. Caso contrário, a diferença mistura transferência federada com quantidade de treino.

08 · Forward e perdas

Cada tarefa usa uma saída diferente

O forward retorna logits de classificação e uma lista de mapas de segmentação em múltiplas escalas. O cliente calcula somente a parte compatível com sua tarefa.

Cliente de segmentação

máscara → deep supervision Dice

Lseg = Σ Dice(output_n, mask) / (n + 1)
  • usa todas as saídas de segmentação;
  • com pesos inversos se configurado;
  • não aplica sigmoid antes do critério;
  • classificação é ignorada.

Cliente de classificação

classe → CE ou Focal

Lcls = Σ critério(logits_n, label)
  • rótulo vira one-hot no multiclasses;
  • pode usar pesos por classe;
  • Focal usa gamma configurável;
  • máscara é ignorada.
09 · Servidor

Como os updates são combinados

Antes de calcular a média, o servidor valida que todos os arrays compartilhados têm as mesmas formas. Depois aplica o modo de agregação configurado e registra o peso efetivo de cada cliente.

Hierárquica · principal

Normaliza os clientes dentro de cada dataset e só então mistura datasets pelos pesos configurados.

■ BUSI 50%■ ISIC 50%

Flat · ablação

Normaliza todos os clientes em um único nível. Com num_examples e pesos de tarefa 1, equivale ao FedAvg amostral.

participação depende do peso base
peso_base = fator_cliente × peso_tarefa
fator_cliente = 1 ou num_examples
peso_final_hierárquico = peso_dataset × normalização_interna
Na configuração principal, client_weighting=uniform, tarefas seg:cls = 4:1 e datasets BUSI:ISIC = 1:1. Com dois clientes por tarefa, cada dataset recebe 50% e, dentro dele, seg recebe 80% e cls 20%.
10 · Checkpoints e retomada

O que é salvo a cada fold

Os workers Flower são efêmeros, então o estado local precisa sobreviver no disco. A retomada verifica se todos os clientes e o tronco global chegaram à rodada esperada antes de reutilizar o fold.

fold_<k>/
├── global_shared.pt          # tronco global da última rodada; apenas federado
├── aggregation_history.json # pesos, participação e exposição por rodada
├── client_<id>/
│   ├── state.pt              # optimizer + personalizado, ou modelo local completo
│   ├── best.pt               # melhor validação local; diagnóstico
│   └── metadata.yaml         # seeds, classes, orçamento e contagens
├── <setup>_test_results.csv
└── <setup>_cls_predictions.csv
best.pt não é o artefato final comparado.

A avaliação final usa a última rodada comum: tronco global final + personalizado mais recente no federado, ou modelo local completo da última rodada no standalone.

11 · Execução segura

Da validação ao estudo

O fluxo começa com testes e resolução do plano, passa por smoke tests curtos e só então parte para as execuções completas.

# Testes do pipeline
python -m unittest discover -v

# Resolve configurações; não treina e não recria partição
python -m src.experiments.study_runner --dry-run

# Validação curta: 2 rodadas, fold 0, CPU
python -m src.experiments.study_runner --smoke --seed-profile operational

# Estudo operacional
python -m src.experiments.study_runner --seed-profile operational

# Retoma somente quando há execução incompleta
python -m src.experiments.study_runner --retry-incomplete
Não use --rebuild-partitions sem intenção explícita.

Esse argumento troca o artefato que garante o pareamento entre braços e pode tornar resultados antigos incomparáveis.
